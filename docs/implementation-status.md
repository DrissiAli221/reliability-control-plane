# RCP implementation status

Last code audit: 2026-09-27; local verification refreshed 2026-09-29. This is an evidence-oriented companion to [the architecture plan](architecture-decisions.md), not a substitute for it. “Implemented” means code exists and the relevant local tests pass; it does **not** mean production-ready or deployed. Re-run checks in the active checkout before relying on this snapshot.

## Implemented in the local reference

| Capability | Current evidence and boundary |
| --- | --- |
| Monitor API and persistence | Authenticated create/list/get/pause/resume/delete, owner-scoped reads and mutations, JPA monitor aggregate, PostgreSQL/Flyway migrations. A configurable 25-monitor-per-owner registration cap includes paused monitors; a transaction-scoped PostgreSQL advisory lock prevents concurrent creates from bypassing it. The GET-by-ID route passed both a real local Spring/PostgreSQL smoke test and the Docker-backed Testcontainers integration suite (see verification record). Deletion is owner-scoped and soft: it stops checks, frees both quotas, removes public-page memberships and hides retained evidence. Unpublished jobs are cancelled; late results are acknowledged and discarded. Accepted HTTP statuses can be configured at creation or edited; the default remains 200–399 and each execution snapshots its rule, so historical verdicts and exports are unchanged by later edits. Target/interval editing is not exposed. Probe results optionally record the allowlisted `cf-mitigated: challenge` marker; latest-check and trace views explain it without changing the verdict or storing response bodies/headers. Older probes produce no hint. |
| Scheduling and publication | PostgreSQL due selection with `FOR UPDATE SKIP LOCKED`, unique logical executions, regional jobs, transactional outbox, leases/retries, and local concurrency tests. The scheduler advances past overdue slots rather than producing an unbounded catch-up storm. Probe regions are fixed in code (`eu-west-1`, `us-east-1`); the runtime refuses to start unless its configured job queues cover exactly those regions. |
| Probe/result pipeline | Pure probe engine, local worker adapter, Lambda SQS handler, central result consumer, durable processed-message and logical-result uniqueness. A composite PostgreSQL foreign key binds each result to its scheduled execution's monitor, timestamp, behavior version, job, and region; rejected result transactions do not consume message IDs. ElasticMQ exercises the local SQS-shaped contract; it does not prove AWS parity. |
| Incident decisions | Regional verdict policy, deterministic incident transition policy, database-backed finalization and incident events, with unit/integration and local fault-injection evidence. Security rejections and worker failures are inconclusive rather than target downtime; processing ignores pre-pause results and resets streaks across behavior versions while preserving an open incident. |
| Availability and reports | Measured availability separated from SLO target and evidence coverage; pending/missing schedule slots reduce coverage, and recorded paused periods are excluded. Owner-only JSON/HTML reports share one calculation model. No PDF or contractual SLO semantics. |
| Status and UI | Explicitly published status-page read projection and a thin React/Vite operator dashboard: a monitor table with 30-day day bars, a per-monitor detail page (45-day bars, per-region 24-hour latency, recent checks, incidents), and a public page with 45-day history. Each check has a trace (every stage timestamp from due time to incident evaluation, shown as a timeline and an event history), the detail page draws the incident state machine from the persisted streak counters, a Pipeline page shows owner-scoped stage counts and throughput, and metric cards explain their formulas with the monitor's own numbers. In the local profile a fault-drill control drives the existing fault-injection endpoint; it is absent elsewhere. Day buckets and their status (`OUTAGE` on any confirmed DOWN, `DEGRADED` on regional disagreement, inconclusive checks never counted as failure) are computed in Java from PostgreSQL time, not in the browser. An unresolved open incident takes precedence over `PAUSED`, `STALE`, and old behavior-version evidence. Otherwise a paused monitor is `PAUSED`; an enabled monitor without recent evidence is `STALE`; a resumed monitor needs new-version evidence. Freshness uses PostgreSQL time and the larger of two check intervals and one interval plus timeout (rounded up to seconds) plus 60 seconds. The public UI refreshes every 30 seconds with a 10-second request timeout and hides old green status on failed or hung refresh; the API disallows caching. Static hosting is declared in Terraform, not deployed. |
| Local observability and recovery | Structured logs, Actuator/Micrometer, local OpenTelemetry/Prometheus/Grafana/Tempo configuration, a k6 scenario, and an isolated local PostgreSQL restore exercise. These are local experiments, not capacity, failover, or RPO/RTO proof. |
| Target URL protection | HTTP(S) and default ports only, user-info/fragment/query rejection, DNS/IP filtering on API acceptance and at the worker's connection, no redirects, bounded body reads, GET-only requests. The address policy conservatively rejects IANA special-purpose IPv4 samples and IPv6 outside current global-unicast space plus named special ranges; an adversarial corpus and rebinding test are local evidence, not a network egress boundary. The worker checks URL syntax before the request and validates the one DNS answer set handed to the socket connector. A whole-request cancellation deadline is tested against a trickling body; DNS cancellation and AWS Lambda timing remain unproven. |

The query-string rule was tightened after the initial local implementation. A monitor stored earlier with a query-bearing URL is not silently rewritten; its future worker attempts are rejected as `UNSAFE_TARGET` and no longer count as target downtime until the owner creates a compliant monitor. Review existing data before any deployment or migration.

## Partial or not implemented from the plan

| Area | Precise gap | Consequence / next proof |
| --- | --- | --- |
| AWS execution | Terraform declares central and regional resources, but no AWS apply, real SQS/Lambda/Cognito smoke test, dashboard upload, or AWS telemetry proof has occurred. | Do not claim deployed geographic monitoring or AWS operational behavior. Deployment requires Ali's account, budget, domain/certificate, state backend, artifacts, and explicit authorization. |
| SSRF defense in depth | Regional worker network egress isolation and deny tests are absent. Client-side peer verification and DNS/TLS/first-byte timing controls are not all independently proven; a local trickle test covers the whole-request deadline but not DNS hangs or AWS execution timing. | Do not open target registration to untrusted public users. Validate a regional egress design, denied private/metadata paths, and limits in the actual worker environment. |
| Monitor lifecycle | Create/list and owner-only pause/resume exist with database-backed enabled-period history. Target/interval editing, deletion, and per-monitor region policy are not exposed. | Before supporting those edits, preserve immutable target/incident-policy snapshots and test that old results keep their original meaning. |
| SLO product model | Target percentage is a report parameter, not a versioned SLO record. Maintenance windows, retroactive-change prevention, late correction versions, regional SLIs, and auditable policy changes are absent. | Reports are reference measurements, not contractual SLO statements. |
| Abuse and audit controls | The registration-count cap is implemented and locally concurrency-tested, but subject/target request rate limits, append-only security audit events, and an operator DLQ redrive workflow are not complete. | A count cap does not bound probe rate for registered monitors or protect against request floods; these remain gates for hostile multi-tenant/public use. |
| Documentation and verification | A local diagnostic runbook, checkout-grounded threat model, [OpenAPI contract](openapi.yaml), [accepted ADR record](accepted-adrs.md), and [simulated local fault-drill postmortem](local-fault-drill-postmortem.md) exist; AWS procedures and threat mitigations are not verified. The full planned adversarial/property-test corpus remains incomplete: an exhaustive short-trace incident state-machine test and SSRF address/rebinding corpus are present, but broader properties and failure combinations are not. A CI workflow is authored but cannot be proven on GitHub until a remote exists and runs it. | Verify CI and expand proofs before making claims beyond the tested local reference. |
| Production resilience | The control plane and source-of-truth database are single-region; the example RDS is Single-AZ and uses the managed master login at runtime. | Geographic probes are not multi-region control-plane HA. Durable use needs least-privilege DB roles, explicit RPO/RTO, restore/failover proof, and reviewed availability/cost design. |

## Future upgrades (designed, deliberately not built)

| Upgrade | Why | Design sketch |
| --- | --- | --- |
| Fair capacity | The demo caps 30 live monitors across all accounts and 5 per account, and every new account gets an automatic `Example` monitor. A visitor can sign up and find the demo already full, mostly with abandoned monitors. | Count only running monitors toward the global cap (paused ones cost nothing); pause monitors of accounts not seen for 7 days, keeping their history; lower the per-account share to 3; stop auto-creating `Example` and offer it as a button instead; make the "full" message point to the read-only demo workspace. Needs a per-account "last seen" column. |
| Follow shared monitors | Each account that wants to see example data creates its own identical checks, so cost grows with visitors, not with distinct targets. | A small `owner_follows(owner_subject, monitor_id)` table grants read-only access to the demo workspace's monitors. They appear as "Shared · demo" with full history, run no extra checks and use no slots. |
| Deduplicate checks by target | At scale, many owners watch the same URL; one check per unique target would make cost track distinct sites. | Share raw regional results between monitors with identical target and probe settings, and keep verdicts, incidents and error budgets per monitor on top of them. Requires reference-counted pause/delete and a scheduler, outbox and incident pipeline that no longer assume one execution belongs to one monitor. Not worth the risk for a demo with a handful of users. |

## How to verify the local claim

With Docker running and Java 21 selected, run `rcp-control-plane/mvnw verify` from the repository root. In `rcp-dashboard`, run `npm test -- --run`, `npm run lint`, and `npm run build`. Follow the root README for the live local pipeline, k6, and restore exercise. A green local suite proves the exercised contracts only. It does not prove AWS IAM, routing, Lambda cold starts, region placement, egress denial, RDS recovery, or production performance.

## Local verification record — 2026-09-29

- With Docker Desktop running, the Java 21 Maven reactor `verify` passed after the GET-by-ID addition: 128 tests, 0 failures, 0 errors, 0 skipped across the modules. The earlier attempt that day failed because Docker was stopped; its Testcontainers context errors were environmental, not a passing or failing code assertion.
- The dashboard passed 10 Vitest tests, ESLint, and a production Vite build. Terraform `fmt -check -recursive`, `validate`, and an offline `plan -refresh=false` with fake local credentials passed; the plan proposed 80 creates and was **not** applied. No AWS call or deployment was used as proof.
- The documented local Spring profile started against Compose PostgreSQL/ElasticMQ with the OpenTelemetry Java agent after first installing the sibling `rcp-probe-core` module into the local Maven cache. The missing install step was found during this run and added to the README. Prometheus reported the control-plane scrape target `up`; Tempo's search API returned control-plane traces. Tempo's `/ready` endpoint returned 503 (`waiting for 15s after being ready`) during the check despite successful trace queries, so readiness was not claimed.
- The existing `Local end-to-end proof` monitor was used for an authenticated incident drill. Injected HTTP 503 responses opened an incident and the published local status page showed `OUTAGE`; restoring pass-through probing resolved the incident and the page showed `OPERATIONAL`. The local region names were simulated, not geographic evidence.
- The 40-second k6 operator-read experiment passed: 1,203 requests, 401 completed iterations, 0 failed requests, 0 dropped iterations, p95 20.77 ms. During the workload, scheduling increased by 2, stored probe results by 4, and runtime loop failures by 0. See ignored machine-local `artifacts/load-tests/20260929T123039Z/report.md`.
- An isolated PostgreSQL 17.6 backup/restore exercise passed after stopping Spring: nine migrations and core table counts matched, with zero orphaned core rows. See ignored machine-local `artifacts/recovery-tests/20260929T123629Z/report.md`. This does not establish RDS recovery or production RPO/RTO.
- The live JSON and HTML report endpoints responded for the owned monitor. An hour spanning prior application downtime had only 2.5% evidence coverage and `sloMet: null`; the system correctly did not present its 100% measured availability as a supported SLO pass.
- The monitor resource's missing GET handler was added so a successful POST `Location` is dereferenceable by its owner. A separate temporary local PostgreSQL cluster ran the actual Spring/Flyway/JPA path with queue loops disabled: POST returned `/api/monitors/{id}`, owner GET returned the monitor, cross-owner GET returned 404, and anonymous GET returned 401. The temporary application and database server were stopped afterward. After Docker recovered, the added Testcontainers integration test and full reactor rerun passed. The first Docker image build had failed in a dependency-prefetch layer during a host disk-space shortage. The Dockerfile was simplified to build the same application artifact inside the container with a BuildKit Maven cache mount; `docker build -f rcp-control-plane/Dockerfile -t rcp-control-plane:local .` then succeeded. The resulting image is configured to run as UID/GID `10001:10001`. No Docker cache or volume data was pruned, and this image build is not a deployed-container smoke test.
- The packaged `rcp-control-plane-0.0.1-SNAPSHOT-exec.jar` also started under Java 21 against that temporary PostgreSQL cluster; its readiness endpoint returned `UP` and an authenticated monitor list returned the test monitor. This verifies the executable JAR startup path, not the Docker image or queue-processing behavior in that disabled-loop smoke run.
- Follow-up verification: Testcontainers was running PostgreSQL 18.6 via `postgres:latest` while Compose, the restore exercise, and RDS use 17.6; the test image is now pinned to `postgres:17.6`. The full reactor `verify` then passed with 130 surefire tests, 0 failures, 0 errors.
